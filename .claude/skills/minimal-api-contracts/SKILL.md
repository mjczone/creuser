# Creuser Minimal API Contracts

Every HTTP endpoint in Creuser conforms to a single contract: success responses use the `ApiResult<T>` envelope, failure responses use RFC 7807 ProblemDetails, and the endpoint's return type is statically typed via `Results<...>` so OpenAPI accurately documents both shapes. This skill explains the contract and how to apply it consistently.

## The contract in one sentence

Success → `200 OK` with body `{ "result": <T> }`. Failure → RFC 7807 ProblemDetails (`application/problem+json`) with appropriate status code, type URI, and structured `errors` extension when applicable.

There are no exceptions to this contract. Endpoints that return raw values, untyped results, or non-RFC-7807 error bodies are bugs.

## Success: the ApiResult<T> envelope

Every successful response wraps its payload in a single-property object:

```json
{ "result": <T> }
```

Where `T` is `string | number | boolean | object | array`. This is uniform — even a single boolean uses the envelope:

```json
{ "result": true }
```

The C# representation is a record:

```csharp
public sealed record ApiResult<T>(T Result);
```

The TypeScript representation, generated by `@hey-api/openapi-ts`, is:

```typescript
interface ApiResult<T> { result: T }
```

### Why an envelope?

Three reasons that compound: (1) frontends always know how to unwrap (single code path: `response.result`); (2) future additions like `meta`, `warnings`, or `links` extend the envelope without breaking clients; (3) it visually distinguishes a successful payload from a ProblemDetails on the wire, even before status code inspection.

### When T is a list

Lists are returned wrapped, like everything else. The envelope is `{ "result": [...] }`, NOT `{ "result": { "items": [...] } }`. If pagination is needed, the result becomes a paginated object:

```csharp
public sealed record Page<T>(
    IReadOnlyList<T> Items,
    int TotalCount,
    int Page,
    int PageSize);

// Endpoint returns ApiResult<Page<Workspace>>
// Wire format: { "result": { "items": [...], "totalCount": 142, "page": 1, "pageSize": 20 } }
```

### When T is void / no payload

Return `ApiResult<bool>` with `result = true`, NOT a 204 No Content. The envelope contract is more important than HTTP semantic purity here — clients always parse a body, never special-case a missing one.

```csharp
return TypedResults.Ok(new ApiResult<bool>(true));
```

## Failure: RFC 7807 ProblemDetails

Every error response is a ProblemDetails document with `Content-Type: application/problem+json`. The standard fields:

```json
{
  "type": "https://creuser.dev/problems/workspace-not-found",
  "title": "Workspace not found",
  "status": 404,
  "detail": "No workspace exists with ID '7c2a...'",
  "instance": "/api/workspaces/7c2a-...",
  "errors": { ... },
  "traceId": "00-abc123..."
}
```

Field guidance:

- `type` — A URI that identifies the problem class. Use `https://creuser.dev/problems/{slug}` where `{slug}` is a stable kebab-case identifier. This is what clients pattern-match on, NOT the title or detail.
- `title` — Short, human-readable, NEVER varies for a given type.
- `status` — Matches the HTTP status code.
- `detail` — Specific to this occurrence; can include identifiers, parameter values, etc.
- `instance` — The request path that produced the error (set automatically by ASP.NET).
- `errors` — Extension field for validation errors. Map of field name → array of error messages. Used for `400 Bad Request` from validation.
- `traceId` — The OpenTelemetry trace ID, for correlating with logs.

### Standard problem types in Creuser

These are the canonical types the platform uses. Add new ones via the `Problems` static class (see helpers below) rather than inlining type URIs in endpoint code.

| Type slug | HTTP status | When |
|---|---|---|
| `validation-failed` | 400 | Request body or parameters failed validation |
| `unauthorized` | 401 | Missing or invalid credentials |
| `forbidden` | 403 | Authenticated but lacks permission |
| `not-found` | 404 | Resource does not exist |
| `workspace-not-found` | 404 | Specific to workspaces — preferred over generic not-found when applicable |
| `job-script-not-found` | 404 | Specific to job scripts |
| `workflow-not-found` | 404 | Specific to workflows |
| `run-not-found` | 404 | Specific to runs |
| `conflict` | 409 | Generic conflict (concurrent modification, duplicate name, etc.) |
| `workspace-busy` | 409 | Workspace lock held by another operation |
| `unprocessable-entity` | 422 | Request is well-formed but semantically invalid (e.g. workflow references nonexistent job) |
| `rate-limited` | 429 | Too many requests |
| `internal-error` | 500 | Unexpected server error |
| `agent-budget-exceeded` | 502 | LLM call exceeded token or step budget |
| `agent-provider-error` | 502 | Underlying LLM provider returned an error |
| `service-unavailable` | 503 | Postgres or Redis unreachable |

Prefer specific types over generic ones. `workspace-not-found` carries more information for a client than `not-found`.

## Typed return shape

Every endpoint declares its full return shape using `Results<...>`. This is what makes OpenAPI accurate and what makes hey-api generate type-safe TypeScript.

```csharp
app.MapGet("/api/workspaces/{id}",
    async Task<Results<Ok<ApiResult<Workspace>>, ProblemHttpResult>> (
        Guid id,
        IWorkspaceService workspaces) =>
    {
        var workspace = await workspaces.FindAsync(id);
        if (workspace is null)
            return Problems.WorkspaceNotFound(id);

        return TypedResults.Ok(new ApiResult<Workspace>(workspace));
    })
    .WithName("GetWorkspace")
    .WithTags("Workspaces");
```

The return type encodes every possible response: success body shape AND every error shape. OpenAPI sees all of them. Generated TypeScript surfaces all of them. The compiler enforces it.

When an endpoint can return multiple status codes from different conditions, list each:

```csharp
async Task<Results<
    Ok<ApiResult<JobScript>>,
    ProblemHttpResult,           // 404 not found
    BadRequest<ProblemDetails>,  // 400 validation
    Conflict<ProblemDetails>     // 409 name conflict
>>
```

### Avoiding the `IResult` escape hatch

NEVER use `IResult` as the declared return type. NEVER use `Results.Ok(...)` (lowercase). These erase the type information and break OpenAPI/hey-api. Always use:

- `Task<Results<...>>` declared return type
- `TypedResults.Ok(...)`, `TypedResults.NotFound(...)`, etc. (capitalized `TypedResults`)

## The Problems helper

Centralize ProblemDetails construction in a static helper. Endpoint code should never construct `ProblemDetails` inline — it should call a method on `Problems`.

```csharp
public static class Problems
{
    private const string TypeBase = "https://creuser.dev/problems/";

    public static ProblemHttpResult ValidationFailed(IDictionary<string, string[]> errors)
        => TypedResults.Problem(new ProblemDetails
        {
            Type = TypeBase + "validation-failed",
            Title = "One or more validation errors occurred",
            Status = StatusCodes.Status400BadRequest,
            Extensions = { ["errors"] = errors }
        });

    public static ProblemHttpResult WorkspaceNotFound(Guid id)
        => TypedResults.Problem(new ProblemDetails
        {
            Type = TypeBase + "workspace-not-found",
            Title = "Workspace not found",
            Status = StatusCodes.Status404NotFound,
            Detail = $"No workspace exists with ID '{id}'."
        });

    public static ProblemHttpResult WorkspaceBusy(Guid id, string heldBy)
        => TypedResults.Problem(new ProblemDetails
        {
            Type = TypeBase + "workspace-busy",
            Title = "Workspace is currently in use",
            Status = StatusCodes.Status409Conflict,
            Detail = $"Workspace '{id}' is locked by operation '{heldBy}'.",
            Extensions = { ["heldBy"] = heldBy }
        });

    public static ProblemHttpResult AgentBudgetExceeded(int stepCount, int tokenCount)
        => TypedResults.Problem(new ProblemDetails
        {
            Type = TypeBase + "agent-budget-exceeded",
            Title = "Agent exceeded its execution budget",
            Status = StatusCodes.Status502BadGateway,
            Detail = $"Agent halted after {stepCount} steps and {tokenCount} tokens.",
            Extensions =
            {
                ["stepCount"] = stepCount,
                ["tokenCount"] = tokenCount
            }
        });

    // ... one method per problem type
}
```

When adding a new problem type: add a method to `Problems`, add the slug to the type registry table in this skill, update the integration tests.

## Validation

Use FluentValidation (registered in DI). The endpoint validates the request, and on failure returns ValidationFailed:

```csharp
app.MapPost("/api/workspaces",
    async Task<Results<Ok<ApiResult<Workspace>>, ProblemHttpResult>> (
        CreateWorkspaceRequest request,
        IValidator<CreateWorkspaceRequest> validator,
        IWorkspaceService workspaces) =>
    {
        var validation = await validator.ValidateAsync(request);
        if (!validation.IsValid)
            return Problems.ValidationFailed(validation.ToDictionary());

        var workspace = await workspaces.CreateAsync(request);
        return TypedResults.Ok(new ApiResult<Workspace>(workspace));
    });
```

The validation error body shape:

```json
{
  "type": "https://creuser.dev/problems/validation-failed",
  "title": "One or more validation errors occurred",
  "status": 400,
  "errors": {
    "name": ["Name is required.", "Name must be 100 characters or fewer."],
    "repositoryUrl": ["Repository URL must be a valid HTTPS or SSH URL."]
  }
}
```

## OpenAPI annotations for hey-api compatibility

Native `Microsoft.AspNetCore.OpenApi` (the .NET 10 implementation, NOT Swashbuckle) is configured. Annotations needed for clean TypeScript generation:

```csharp
app.MapGet("/api/workspaces/{id}", ...)
    .WithName("GetWorkspace")          // Becomes the TS function name
    .WithTags("Workspaces")            // Groups in Scalar UI and in generated TS
    .WithSummary("Get a workspace by ID")
    .WithDescription("Returns full workspace configuration and current status.")
    .Produces<ApiResult<Workspace>>(StatusCodes.Status200OK)
    .ProducesProblem(StatusCodes.Status404NotFound);
```

`Produces<T>` and `ProducesProblem` are usually inferred from the `Results<...>` return type and don't need to be specified — verify by checking the generated `openapi.json`. Add them explicitly only when the inference is wrong.

### Naming conventions for hey-api output

- Endpoint name → TypeScript function name (PascalCase to camelCase): `GetWorkspace` → `getWorkspace()`
- Tag → TypeScript file group: `Workspaces` → `services/workspaces.ts`
- Request DTO name → TypeScript interface: `CreateWorkspaceRequest` → `CreateWorkspaceRequest`
- Response payload type → wrapped in `ApiResult<T>`

Always name endpoints. Unnamed endpoints generate ugly anonymous TypeScript.

## Common scenarios with examples

### GET single resource with NotFound

```csharp
app.MapGet("/api/workspaces/{id}",
    async Task<Results<Ok<ApiResult<Workspace>>, ProblemHttpResult>> (
        Guid id,
        IWorkspaceService workspaces) =>
    {
        var workspace = await workspaces.FindAsync(id);
        return workspace is null
            ? Problems.WorkspaceNotFound(id)
            : TypedResults.Ok(new ApiResult<Workspace>(workspace));
    })
    .WithName("GetWorkspace")
    .WithTags("Workspaces");
```

### GET list with pagination

```csharp
app.MapGet("/api/workspaces",
    async Task<Ok<ApiResult<Page<Workspace>>>> (
        int page,
        int pageSize,
        IWorkspaceService workspaces) =>
    {
        var result = await workspaces.ListAsync(page, pageSize);
        return TypedResults.Ok(new ApiResult<Page<Workspace>>(result));
    })
    .WithName("ListWorkspaces")
    .WithTags("Workspaces");
```

Pagination parameters are query strings: `?page=1&pageSize=20`. Default to `page=1, pageSize=20` if absent. Cap `pageSize` at 100 server-side regardless of what's requested.

### POST create with validation

```csharp
app.MapPost("/api/workspaces",
    async Task<Results<Ok<ApiResult<Workspace>>, ProblemHttpResult>> (
        CreateWorkspaceRequest request,
        IValidator<CreateWorkspaceRequest> validator,
        IWorkspaceService workspaces) =>
    {
        var validation = await validator.ValidateAsync(request);
        if (!validation.IsValid)
            return Problems.ValidationFailed(validation.ToDictionary());

        try
        {
            var workspace = await workspaces.CreateAsync(request);
            return TypedResults.Ok(new ApiResult<Workspace>(workspace));
        }
        catch (DuplicateWorkspaceException ex)
        {
            return Problems.Conflict(ex.Message);
        }
    })
    .WithName("CreateWorkspace")
    .WithTags("Workspaces");
```

Note: POST returns 200 with the envelope, NOT 201 Created. The envelope contract supersedes HTTP-status-code idioms.

### PUT update (full replacement)

```csharp
app.MapPut("/api/workspaces/{id}",
    async Task<Results<Ok<ApiResult<Workspace>>, ProblemHttpResult>> (
        Guid id,
        UpdateWorkspaceRequest request,
        IValidator<UpdateWorkspaceRequest> validator,
        IWorkspaceService workspaces) =>
    {
        var validation = await validator.ValidateAsync(request);
        if (!validation.IsValid)
            return Problems.ValidationFailed(validation.ToDictionary());

        var workspace = await workspaces.UpdateAsync(id, request);
        return workspace is null
            ? Problems.WorkspaceNotFound(id)
            : TypedResults.Ok(new ApiResult<Workspace>(workspace));
    })
    .WithName("UpdateWorkspace")
    .WithTags("Workspaces");
```

### DELETE

```csharp
app.MapDelete("/api/workspaces/{id}",
    async Task<Results<Ok<ApiResult<bool>>, ProblemHttpResult>> (
        Guid id,
        IWorkspaceService workspaces) =>
    {
        var deleted = await workspaces.DeleteAsync(id);
        return deleted
            ? TypedResults.Ok(new ApiResult<bool>(true))
            : Problems.WorkspaceNotFound(id);
    })
    .WithName("DeleteWorkspace")
    .WithTags("Workspaces");
```

### Action endpoint (verb-shaped)

When an endpoint represents an action rather than a resource (e.g. running a workflow), use a verb in the path and POST:

```csharp
app.MapPost("/api/workflows/{id}/run",
    async Task<Results<Ok<ApiResult<RunStarted>>, ProblemHttpResult>> (
        Guid id,
        RunWorkflowRequest request,
        IWorkflowService workflows) =>
    {
        var run = await workflows.StartRunAsync(id, request);
        return run is null
            ? Problems.WorkflowNotFound(id)
            : TypedResults.Ok(new ApiResult<RunStarted>(run));
    })
    .WithName("RunWorkflow")
    .WithTags("Workflows");

public sealed record RunStarted(Guid RunId, DateTimeOffset StartedAt);
```

The response payload tells the client what happened (run was created, here's its ID). The action is in the path; the verb is in HTTP semantics.

### Async operation that may take time

For operations that complete within request scope but might be slow (a few seconds), the endpoint blocks. For operations that take longer, return immediately with a job ID:

```csharp
// Returns immediately; client polls /api/runs/{id} for status
app.MapPost("/api/workspaces/{id}/sync",
    async Task<Results<Ok<ApiResult<SyncStarted>>, ProblemHttpResult>> (
        Guid id,
        ISyncService sync) =>
    {
        var jobId = await sync.EnqueueSyncAsync(id);
        return TypedResults.Ok(new ApiResult<SyncStarted>(new SyncStarted(jobId)));
    });
```

Long-running operations NEVER block the request. They return a job ID and the client polls or subscribes via SSE/WebSocket.

## Anti-patterns to avoid

**Returning naked types.** `Task<Workspace>` or `Task<IResult>` erases type info. Always declare `Task<Results<Ok<ApiResult<T>>, ...>>`.

**Returning naked envelope content.** `return TypedResults.Ok(workspace)` is wrong; the result must be wrapped: `return TypedResults.Ok(new ApiResult<Workspace>(workspace))`.

**Constructing ProblemDetails inline.** Use `Problems.X(...)`. Never inline a new `ProblemDetails { ... }` in endpoint code.

**Throwing exceptions for control flow.** Don't throw `NotFoundException` and let middleware translate it. Return the ProblemDetails directly. Exceptions are for actually-unexpected conditions, which become 500 Internal Error via global handling.

**Inconsistent error type slugs.** Don't use `https://creuser.dev/errors/...` in one place and `https://creuser.dev/problem-types/...` in another. The base is `https://creuser.dev/problems/`. Always.

**Mixing 204 No Content with the envelope.** Either every endpoint returns the envelope (preferred) or none do. Don't be inconsistent. Creuser's choice: every endpoint returns the envelope, even for "void" results.

**Using the lowercase `Results.X(...)` factory methods.** Always `TypedResults.X(...)`. This is the difference between a clean OpenAPI spec and a useless one.

**Hand-writing TypeScript clients.** They get out of sync. Always run `npm run codegen` after backend changes that affect endpoints, request/response DTOs, or problem types.

```
│   └── UpdateWorkspaceRequestValidator.cs

```

Group endpoints by resource. One static class per resource with an extension method `MapWorkspaceEndpoints(this IEndpointRouteBuilder)` that registers all endpoints for that resource.

```csharp
public static class WorkspaceEndpoints
{
    public static IEndpointRouteBuilder MapWorkspaceEndpoints(this IEndpointRouteBuilder app)
    {
        var group = app.MapGroup("/api/workspaces").WithTags("Workspaces");

        group.MapGet("/", ListWorkspaces).WithName("ListWorkspaces");
        group.MapGet("/{id}", GetWorkspace).WithName("GetWorkspace");
        group.MapPost("/", CreateWorkspace).WithName("CreateWorkspace");
        group.MapPut("/{id}", UpdateWorkspace).WithName("UpdateWorkspace");
        group.MapDelete("/{id}", DeleteWorkspace).WithName("DeleteWorkspace");
        group.MapPost("/{id}/sync", SyncWorkspace).WithName("SyncWorkspace");

        return app;
    }

    // Endpoint handler methods follow...
}
```

In `Program.cs`:

```csharp
app.MapWorkspaceEndpoints();
app.MapJobScriptEndpoints();
app.MapWorkflowEndpoints();
app.MapRunEndpoints();
```

This keeps `Program.cs` clean and lets each endpoint group own its routing, naming, and tagging conventions.

## AI capability discovery

The in-app AI assistant uses a `CapabilityRegistry` (`src/Creuser.Web/Agents/Capabilities/`) to know what the platform can do. When a user asks "where do I X" or "what can I do here", the assistant calls `navigate(intent)` or `describe_capabilities(topic)`, which read from this registry, and emits markdown links back to the relevant settings pages.

**The rule: when you add or change a user-facing endpoint, decide whether it represents a discoverable capability. If yes, add a `Capability` entry alongside.**

Today the catalog is a hand-curated list in `CoreCapabilityProvider.cs`. Edit it in the same PR as the endpoint — the file's comments call out that responsibility. Future iterations will move the catalog to `[AiCapability]` attributes on the endpoint methods themselves (compile-time scanner builds the list automatically) and then to per-workspace / plugin-contributed `ICapabilityProvider` implementations. The shape stays the same regardless of source; only the discovery mechanism evolves.

### When does an endpoint warrant a capability entry?

Yes when:
- It corresponds to a settings surface or admin action a user might *describe in plain language* ("invite a user", "set the API key").
- It mutates user-visible state (`POST /api/admin/users/{id}/role` → "promote to admin").
- It's a top-level navigation target (`/settings/branding`, `/settings/environment`).

No when:
- It's a primitive read endpoint that's only consumed by the SPA (`GET /api/auth/me`, `GET /api/branding`). These power the UI; they're not the user's mental model.
- It's a low-level RPC the user would never invoke directly (`POST /api/branding/assets/logo` is hit by the LogoUploadField, not by the user "calling an asset upload endpoint").
- It's an internal health/diagnostic surface (`/api/ping`, `/api/agents/health`).

The test: would a non-engineer user describe their intent in a way that maps to this? If yes, capability. If they'd describe their intent at a *higher level*, the capability lives on that higher-level container instead.

### Capability shape

```csharp
new Capability(
    Id: "users.manage",                     // stable, kebab-case, dot-namespaced by topic
    Topic: "users",                         // groups capabilities — the assistant filters by this
    Title: "Manage user accounts",          // short label for navigation buttons
    Description: "Reset passwords, toggle roles between Admin and User, deactivate or delete accounts. The last remaining admin can't be demoted, deactivated, or deleted.",
    Intents:                                // free-text phrases an operator might type
    [
        "reset password",
        "change role",
        "promote user",
        "demote user",
        "deactivate user",
        "delete user",
        "remove user",
    ],
    Route: "/settings/users",               // SPA route the user lands on
    ExpandSection: null,                    // optional q-expansion-item key to auto-open via ?expand=
    RequiresRole: Roles.Admin,              // assistant filters out entries the user can't act on
    Mutates: true                           // (future) tools-that-write require UI confirmation
)
```

### When to add a new topic

Topics are coarse — `users`, `branding`, `environment`, `account`, `workspaces`. Don't fragment into per-feature topics; the assistant uses topics to filter `describe_capabilities("topic")` calls, and an over-fragmented set defeats that. Add a new topic only when adding a whole new section of the platform (e.g. when workspaces land).

### Page-side: ?expand= query handling

When a capability's `ExpandSection` is set, the link the assistant emits looks like `[Anthropic API key](/settings/environment?expand=aiAnthropic)`. The destination page must:

1. Read `route.query.expand` on mount.
2. Set the matching key in its persisted `useLocalStorage('creuser.<page>.expanded.vN', { ... })` to `true`.
3. If the section is nested under a parent, expand the parent too.
4. Scroll the section into view via `[data-section-key]` and `scrollIntoView`.

See `EnvironmentPage.vue` and `BrandingPage.vue` for the canonical pattern. The `data-section-key` attribute on each `q-expansion-item` / `CollapsibleSection` is what makes targeted scroll work.

### Security boundary

Capabilities sent to the LLM are **filtered by user role first**. A `User`-role caller never sees `Admin`-only capabilities — protects against the assistant suggesting actions the user can't perform AND avoids leaking the existence of admin features to non-admins. The filter lives in `CapabilityRegistry.GetAvailableAsync` — don't add capabilities with sensitive descriptions and rely on UI-level gating; the registry is the trust boundary.

## Verification checklist

Before considering an endpoint done:

- [ ] Return type is `Task<Results<...>>` with all possible response shapes listed
- [ ] Success path uses `TypedResults.Ok(new ApiResult<T>(...))`
- [ ] Error paths use `Problems.X(...)` factory methods
- [ ] Endpoint has `.WithName(...)` and `.WithTags(...)`
- [ ] Request DTO has a FluentValidation validator if it has any constraints
- [ ] No `IResult` or lowercase `Results.X` anywhere
- [ ] OpenAPI doc at `/openapi/v1.json` shows the endpoint with correct request and response schemas
- [ ] Generated TypeScript (`npm run codegen` in `src/Creuser.Web.Spa/`) compiles without errors
- [ ] Integration test covers happy path AND at least one error path
- [ ] If a new problem type was introduced: added to `Problems` class, added to type registry table
- [ ] If the endpoint is user-facing: corresponding `Capability` added to `CoreCapabilityProvider` (or attribute when the scanner lands), with `Intents` covering at least 3-4 phrasings an operator might use
